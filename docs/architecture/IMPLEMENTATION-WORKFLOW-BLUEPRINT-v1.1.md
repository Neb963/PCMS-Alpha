## 1. Organize work around operator outcomes

Implement the smallest durable coordinator over working components. Do not recreate I00–I17 as a second sequential checklist, add a workflow engine, or rewrite the donor/executor/UI shell. Stage 7's security, uncertainty, source and independent CI principles remain valuable; its phase and per-step policies require the explicit transition described in the migration plan.

GB-01–GB-05 refine the existing nine slices; they add no new phase process. Preserve the small coordinator, exclusive donor authority and accepted product behavior. M0 preservation is per affected profile/shared resource; missing original I17 evidence cannot veto detached disposable work. The original batch `batch_e2c328e54f9c4a6ab89f1084134fde52` remains quarantined against automatic CREATE/RENAME from every origin.

Each slice must advance a complete operator journey through actual production entrypoints, canonical stores and independent observations. A set of importable modules, a checklist UI, a synthetic HTTP ACK or a test named after an AC is not a completed journey. Shared foundations may precede visible completion, but their proof must serve an identified journey. Keep the accepted AC/T/E matrix independent of implementation code.

Do not let one failing account/native/Git scope park unrelated known-safe work. Do not declare a slice accepted while its indispensable capability is mocked and never proved at the required tier. A safe disabled capability may be an honest checkpoint, not product completion.

### 2.1 Minimum rules for the future entry file

The future `AGENTS.md` should convey these rules in plain language:

1. Work only within the currently authorized slice and repositories; inspect real branch/PR state before changing anything. Preserve unrelated work and signed originals. Compatible cross-module fixes within the journey are expected; product-policy changes require explicit client amendment.
2. PersonaMonkey owns Persona, protected route, tab/control and native routing. No raw donor-state edits, second router, Direct fallback or challenge-driven rotation. GB-01 donor grants are bounded and checked at the actual proxy/blocking-request boundaries; invalidation precedes revocation awaits. Separate new automation holds from safe human-network use. Required unavailable network proof blocks new managed requests, preserving human pages/work.
3. Persist exact intent before effects. A possible effect is reconciled by observation before further writes. Never retry the quarantined original I17 CREATE/RENAME, invent ownership, or move uncertain work to another account.
4. One generator source writer; preserve human dirty work, originals, candidate history and exact bytes/assets. Tests/Git/source/approval converge on the same final F. Native AI has no Git/publication/management authority.
5. Routine runtime work uses accepted standing scope; publication is exact-candidate human approval. PCMS may conditionally write its tested source directly to the source repository's main; coding agents use implementation/source-authoring branches and PR review. No force or auto-merge of relevant source conflicts.
6. Test the real changed boundary and adverse outcome at the proper tier. No live provider/private-source writes in CI. New live/host/Git effects need their actual approved disposable scope. Missing/skipped/inconclusive is not PASS.
7. Preserve remote checkpoints through the connected GitHub path when implementation is authorized; verify ref/tree, not just a commit object. Independent review is mandatory for protected policy changes. Report exact evidence, uncertain outcomes and next action; stop when scope is exhausted or a genuine boundary blocks further work.

This is a content blueprint, not an installed replacement instruction. It proposes replacing the historical one-phase-per-invocation constraint with bounded authorized product slices. It does not authorize autonomous scope expansion or require multiple agents. Independent CI/policy review means a genuinely separate trust authority, not another task under the same author identity.

### 2.2 Work and resume loop

Start from actual repository main, open/draft PRs, exact current slice and checkpoint. Read the relevant client AC/T/E, design section and existing failing evidence. Do not repeat valid Phase B/pilot probes solely to accumulate passes; convert confirmed defects into focused regressions when repairing them.

Inspect the first failing production boundary before rewriting adjacent subsystems. List reused versus changed modules, exact operator outcome, any substituted response and the proof still missing. Implement compatible record/admission repairs with migration/rollback, then run the smallest meaningful checks. Keep a durable draft PR/checkpoint before longer work if authorized. A local file or uploaded commit not reachable from a confirmed branch is not a remote checkpoint.

If a shared guard/store/interface must change, change it with targeted adverse coverage rather than declaring the accepted journey out of scope because it crosses a directory. If an architecture mechanism fails E-01/E-02/E-04/E-06/E-08, stop its dependent implementation/promotion and present the concrete failure plus narrow alternatives. Failed useful eligible-time accrual requires a targeted technical amendment **before S07 scheduler implementation**. Unreviewed A framing or incomplete decrypted recovery prevents S02 format promotion; failed early E-08 prevents dependent restart integration. Independent proven-scope work may continue; the missing original journal holds only unsafe affected migration/reconciliation, not fresh-profile engineering. Do not proceed by weakening the requirement or switching to C without approval.

The handoff record should contain: slice/outcome; branch/PR/exact confirmed SHA and tree; package/donor/host versions where relevant; changed production path; commands and evidence tiers; independent observations and first failure; authority/effect scope; remaining holds; exact next step. Do not put future CI run IDs or a commit's own SHA inside that same commit and call it proof.

## 4. CI shape and trust

Propose one stable required aggregate, such as `pcms-required`, which runs for every PR. Inside it, select exact changed-boundary checks from trusted policy plus risk. Selection and aggregation are themselves tested. Do not use whole-workflow path exclusions that leave required results missing, or let skipped conditional jobs silently mean covered.

| Lane | Content / oracle | When and authority |
|---|---|---|
| Fast D | Build/static/schema validation; fixed transition tests; independent provider/Git object/ref ledgers; corruption/quota/lost-ACK/race/clock negatives; affected donor security tests and source-path/credential redaction. | Every PR, selected by real changed boundaries with a small always-on safety core. No live credentials/network effects. Meaningful failures, not implementation-mirroring assertions. |
| Packaged B | Actual fully enabled combined XPI in pinned isolated Firefox, real IDB and installed extension permissions, startup/suspend/lease/editor/UI, independent loopback source/native/feed oracles. | Required for relevant browser/security/persistence changes and final affected candidate. One isolated browser setup for related tests where safe; no operator profile. |
| Integration / resource | T-01–T-10 against one coordinator, bounded source-heavy queues, complete tree fallback, backup framing/restore faults, fairness and UI accessibility. | Shared-core changes and milestones/main scheduled regression; source sizes/history representative and substitutions explicit. |
| Native H | Narrow host/OS vault/artifact bytes, restore mappings, installed-profile cold process/OS suspend, timed real clock and resource run. | Appropriate controlled local/native environment; separate authorization/setup. Cannot be faked by an ordinary public runner or a stub `secret-tool`. |
| L + GIT acceptance | Minimal real disposable provider/native AI/feed/source/publication and actual authorized Git main/ref/blob readback. | Explicit operator-approved scope only; never unattended public CI or production fallback. Preserve artifacts and reports; publication still waits for human exact approval. |

The aggregate must fail if any selected required job is failed, canceled, missing, wrongly skipped, wrong-SHA or lacks a valid result artifact. Unselected jobs are explicitly not required, not PASS claims. A docs-only PR can pass a truthful selected gate without claiming browser execution. Build provenance records commit/tree, donor, manifest capabilities, package digest, browser and install mode.

Protect trust-root changes: required-check policy, selector/aggregator, workflow privileges, acceptance mapping and agent safety rules cannot self-certify through edited PR-owned CI. Use independent trusted main-sourced validation/reviewer and hold autonomous merge. If actual repository settings cannot enforce that, report it as a bootstrap blocker. A same-account connection or second model run is not independently authorized approval. Routine test improvements do not need a new operator ceremony when existing authorization suffices.

Do not run untrusted PR code with elevated secrets/`pull_request_target` authority. Keep runtime Git tokens/provider sessions/source out of public Actions artifacts and XPI. Pin toolchains/actions/browser where practical and verify current official workflow documentation during later implementation; this blueprint does not claim current branch rules or runner setup are already sufficient.

### 4.1 Real Firefox and restart discipline

Use the actual package with accepted capabilities enabled, not a disabled/shadow build proving “nothing happened.” Log Firefox executable/version, XPI digest, Gecko ID and host boundary substitutions. For full restart, use technical §10's finite owned supervisor/profile and durable outside-browser run ticket. Persistently install the same XPI in the disposable profile under supported test settings and verify its bytes/Gecko ID/version and enabled state before and after an actual OS-observed process-tree exit/new start. A temporary development add-on disappearing at restart cannot prove recovery. Distinguish tab closure, event-page unload, extension reload, crash and real browser exit/relaunch with external evidence.

Test safe shutdown/worker cuts at real awaits, reopening durable IDB rather than passing the same in-memory store to a new function. External native/provider ledgers persist independently of browser state so double writes are observable. Do not assert a true browser restart from a new JavaScript `bootId` alone. Product diagnostic supervisor and CI harness may share the fixed restart receipt format; neither gets arbitrary process control. Prove this in early E-08 B+H during S01, including bridge termination, supervisor survival, wrong-profile capability, competing requests, PID reuse and failure/incomplete-restoration reports. Browser-propagated private capability is an unverified platform assumption. The supervisor is finite/on-demand and cannot supply Refresher uptime. One-time native installation/profile setup is later separately authorized; a user clicking the button after setup does not manually restart Firefox. A missing harness blocks AC-16, not all independent engineering.

### 4.2 Practical test/triage rules

Start from the confirmed defect or missing accepted boundary. Show that the targeted negative case turns the check red, then green after repair. Prefer D for lost ACK/concurrency/clock faults and B/H for actual lifecycle; do not spend live resources reproducing every negative. Test optional TESTING **absence**, actual no-READY creation-only behavior, dirty human edits and candidate successors rather than happy callbacks alone.

Classify failure by first cause: product, oracle/fixture, package/toolchain, environment or race. Inspect exact SHA/job/log, reproduce narrowly, repair and rerun impacted coverage. Broaden only for a changed shared boundary, new failure or unresolved risk. Avoid blanket retries, `continue-on-error`, massive redundant browser suites or silently stale acceptance artifacts. Preserve failing evidence even if the final run passes.

Measure setup/run latency, critical path, flakiness and diagnostic usefulness; optimize duplicate setup and late cheap failures. No arbitrary runtime target is claimed without measurement. Cache pinned binaries/dependencies safely; caches are not provenance. Keep one useful sanitized failure bundle: exact build/scope, state/effect timeline, first failure, independent observations, required missing evidence and recovery action, without raw source, tokens, cookies or chats.

## 5. Acceptance and completion records

One ledger row binds `(contract revision, AC/T/E or retained legacy assertion, build/package, configuration, tier, scope, oracle, outcome, artifact, limitation)`. A generated summary is a projection, not a second manually edited authority. Keep implementation progress separate from evidence status: “code exists,” “D passes,” “B passes,” “L blocked” and “operator accepted” are different facts.

For every complete journey require the accepted negative/recovery trace at its actual boundary. Example: AC-04 needs one standing intent through account protection, real private create/rename/readback, NOT_READY folder and per-item recovery; passing an isolated CREATE API test does not complete it. AC-10/12 needs real same-F tests/writeback/review/publication, including source drift; a queue screenshot and synthetic approval are insufficient. AC-17 needs actual disk bytes independently authenticated/decrypted with **every** source/donor/ownership/recovery dependency reconstructed and same/fresh-profile activation proved. Selected A is not accepted by encryption finalization, a tag from the writer or download metadata alone. Read-only inspect cannot repair host manifests or present an unverified plaintext header as trusted preview.

Reusing evidence is encouraged when behavior, relevant source/build boundary, configuration and tier match. Record that justification once. Do not ask the operator to repeat historical valid work merely because slice names changed; do not reuse old live proof to accept a changed adapter without checking compatibility. Blocked or pending approval stays visible. Known required test failure never changes classification to “infrastructure unavailable” to permit publication.

A useful slice checkpoint says what now works for the operator, why the change was necessary, how it was tested at which tiers, what is still held and the exact next step. A product release requires all applicable AC-01–18 tiers and acknowledged genuine limitations, not a target test count or a green aggregate alone.
