## 2. Adversarial cross-workflow traces
These traces must be exercised against one coordinator, not just isolated API mocks.

**T-01 — Concurrent batch + Git import.** A user submits `alpha` while a merged `main` change adds `generators/alpha/DEPLOYMENT.md`. Both paths resolve to one slug operation. If Git revision changes during initial import review, only changed scope requires new approval; unrelated commits do not. If one remote create ACK is lost, neither origin can issue a second blind create.

**T-02 — Public update + Refresher.** Generator X is ACTIVE and publicly listed when READY arrives. Existing public update waits for sleep. At eligible sleep, source/source-dirty/hold-cap checks precede unlisting; Refresher does not edit while AI writes. Other active generators continue refreshing. Pending human publication cannot automatically publish X or take unbounded additional public sources offline.

**T-03 — New READY during repair.** The current AI candidate A receives external coherent READY B on `main`. Preserve A's work and real provider observations at a safe checkpoint; supersede without auto-merge. Keep old human approval invalid. B becomes eligible under the same update constraints. PCMS's own subsequent tested source writeback is not B2 or an infinite READY loop.

**T-04 — Human editor + marker.** The operator types unsaved content in an existing generator edit tab while Refresher observes recent-page disappearance. Refresher holds and preserves the exact raw source. Later a publication candidate changes the same generator; existing tests/approval cannot authorize overwrite of the human work. UI offers Adopt human changes as new candidate / Defer.

**T-05 — Exit drift + backup restore.** Account A's route resolves to a previously observed exit for B. A's relevant jobs hold. After a stale backup is restored, PCMS must not pretend it recovered any newer exclusion records not present. Restore remains inert pending owner/route verification and explicit activation; unrelated eligible accounts continue. No Direct fallback.

**T-06 — Folder rename + missing-source original.** Git removes `generators/old` and adds `generators/new` with similar content. PCMS does not blindly create or rename. Operator chooses “Create new”: original remote old remains intact with separate identity, source provenance and a missing-Git-source incident; new starts private/unlisted and stages only upon READY. No approval/source blob crosses identities.

**T-07 — Auto-backup and unfinished remote save.** A backup starts while the provider may have saved source but the ACK is lost. Backup records durable intent/unknown result without asserting final remote state. On restore, read-only reconciliation precedes any resumed save. A daily backup success is reported only after a genuinely recoverable artifact exists; the old known-good file is not deleted due to a failed new export.

**T-08 — Incomplete recent feed + rate limit.** A list request returns some entries but incomplete page coverage; an active generator is absent from that partial data. PCMS records `UNKNOWN`, not absent, and does not churn trivial markers. Account-level rate limit affects only that scope. Occupancy reporting includes coverage/unknown data and does not fabricate a page-share metric from a truncated sample.

**T-09 — Postmerge test fixture.** With the now-merged `pcms-test-generator`, first connect shows its path in the exact-scope import preview. Before approval, no Perchance side effect. If approved, creation of an empty, private generator is permissible even though status is `NOT_READY`; AI tests/source staging/publication are not. Existing default prompt is read unchanged, never replaced with a template.

**T-10 — Fresh-profile restore after local removal.** Previous backup contains account Z but newer current state records its local removal. Inspected restore excludes Z by default when that history is reliable; in a wholly fresh profile with no later removal history, explicitly show Z for inclusion choice. Restored account stays inactive until verified reactivation; previous approval and protected exit history do not bypass current checks.

## 3. Engineering proof gates (not additional product decisions)
| Gate | Minimal proof before committing to a design that depends on it | If not proven |
|---|---|---|
| **E-01 Route** | PersonaMonkey API v1 truly provisions/repairs protected distinct Mullvad exits without PCMS managing routing internals; observe actual applicable IPs | Record exact donor/API limit; propose smallest adapter/contract reconciliation, hold affected account |
| **E-02 Source** | Full live generator source including nested/binary owned assets can be enumerated and independently read back, or exact unsupported cases known | Hold affected adoption/update; never record false exact backup |
| **E-03 Provider save** | Native authenticated PCMS marker save and private creation work live, with independent owner/source/listing receipts | Diagnose first causal failure, repair adapter, then retest; no scheduler redesign first |
| **E-04 Clock** | Healthy operational time accrues correctly through real long spans and wake gaps, not only short monitor requests | Correct observer/time model with deterministic+packaged regression |
| **E-05 Git** | `main` tree complete at 1k+, correct new paths, coherent READY identity, guarded direct writeback under actual branch restrictions | Narrow design/credential reconciliation; do not change D1-A without asking |
| **E-06 Backup** | Host-protected unattended key handling, independently checked encrypted file, fresh-profile restore and Persona mapping | Expose impossibility/alternatives for explicit decision, not plaintext shortcut |
| **E-07 Background** | Fully enabled XPI works without dashboard tab, across suspend, Firefox shutdown/startup and bridge outage | Adapt minimal wake/journal integration or raise genuine platform limit |
| **E-08 Diagnostics** | One test action can cover real disposable source and accurately verify cold browser recovery with a suitable harness/handoff | Propose limited operator step as an explicit deviation if unavoidable |
| **E-09 Source/release** | One source actor at a time; exact tested full-source fingerprint and candidate-bound approval; rollback from proven previous good | Hold mutations rather than publish wrong source or use incomplete evidence |

**Path B remains the default**: simplify the existing integrated extension, reuse donor and working libraries, remove ceremonies that do not address real hazards. Path C (thin replacement) requires an explicit comparative cost/risk analysis, not a preference for greenfield simplicity. There is no production backup fleet to migrate; there can still be development state to preserve.

## 4. Acceptance governance

- Gate A product intent and these AC journeys are **accepted**. No current build, XPI, repository CI or live provider state is thereby accepted.
- The technical design and any migration or replacement of signed Stage 7 technical authority require **separate explicit approval**.
- Do not turn one PASS into another: fixture/simulated, packaged browser, host/backup, Git remote and real provider evidence are distinct.
- Execute the smallest real provider test scope authorized by the operator; reuse matching existing evidence rather than repeating low-value tests.
- Any genuinely infeasible journey must be reported with alternative options and a product-level reconciliation **before** silently changing the oracle.
