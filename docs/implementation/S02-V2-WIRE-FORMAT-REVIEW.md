## Binary envelope

All numbers are unsigned big-endian. The first 50 bytes are exactly: magic 50 43 4d 53 42 4b 32 00 (PCMSBK2 plus NUL); version 02 (1 byte); algorithm/KDF ID 01 (1 byte); PBKDF2-SHA256 iterations 0003d090 (4 bytes, exactly 250000); OS CSPRNG salt (16 bytes); OS CSPRNG IV (12 bytes); exact plaintext length (8 bytes). The **entire header** is AES-GCM AAD. Follow with exactly that many bytes of ONE AES-256-GCM ciphertext message and a final 16-byte authentication tag, without trailing data. The NIST single-invocation bound is 2^36−32 plaintext bytes. Every new run gets a fresh salt/IV; never reuse an interrupted session's cipher context. No derived key in storage, diagnostics or ciphertext metadata.

## Authenticated plaintext framing

Each frame is 1-byte tag + 8-byte unsigned big-endian length + exactly length bytes. Valid order: BLOB* → CANONICAL* → DONOR → END. Unknown tags, unexpected ordering, trailing bytes and duplicate entries are invalid. Transport fragments may split these frames at arbitrary offsets. They are NOT separately encrypted or authenticated messages.

- **BLOB / tag 01:** 32 raw bytes of SHA-256 digest followed by original raw file bytes. ID equals SHA-256(raw bytes), including binary assets. At most one occurrence per digest; path is retained in the original source manifest rather than invented from a digest. Candidate frame limit 12 MiB + 32 bytes (matching current source-file bound).
- **CANONICAL / tag 02:** canonical sorted-key UTF-8 JSON with exactly store, key, value and refs. Store is one of entities, operations, events, meta, observations. Key and value retain the exact existing PCMS structured-clone taxonomy (including Undefined, Date, ArrayBuffer, typed arrays). Source-bearing records retain complete original/current/previous-good/candidate/history manifests and identifiers, but their original source blob base64 field is replaced by an exact one-key object with property __pcmsV2BlobRef and the lowercase content SHA-256 value. The refs array contains sorted unique source digests referenced by that row. Never infer bytes from merely a fingerprint. Candidate max 4 MiB per deduplicated metadata row; a legitimate larger record requires independently reviewed continuation, not truncation.
- **DONOR / tag 03:** exactly the original encrypted PersonaMonkey portable backup envelope as raw UTF-8 bytes. The native parser authenticates outer GCM and donor byte SHA; the unchanged donor decoder must independently decrypt and validate this inner envelope before restore. Maximum prototype frame 2 GiB; actual donor headroom is not yet measured.
- **END / tag ff:** UTF-8 sorted-key JSON with EXACTLY schema:2, canonicalRows, storeCounts (all five stores), uniqueBlobs, donorSections:1, sourceRefsSha256, rowDigestsSha256, donorSha256. sourceRefsSha256 hashes sorted lowercase referenced digests joined by LF; the referenced set must exactly equal actual BLOB IDs. rowDigestsSha256 hashes lowercase SHA-256 digests of CANONICAL raw frame payloads, in order, joined by LF. donorSha256 hashes exact DONOR bytes. At most 1 MiB END payload.

JSON key ordering follows JavaScript UTF-16 lexical key ordering. The native parser rejects duplicate and out-of-order object keys, invalid UTF-8, nonfinite number tokens, malformed/oversized frames, duplicate row identities, mismatched content digests and terminal inventory. Parser limits are checked from the header BEFORE metadata allocations: up to 100,000 CANONICAL rows and 100,000 unique blobs per candidate. These explicit resource bounds remain subject to real fleet sizing and independent review; none permit omitting evidence. Large numeric JSON canonicalization/interoperability and oversized legitimate single-record continuation remain review findings, not silently accepted constraints.

## Effect, verification and restoration boundary

The fixed-purpose native candidate uses host-selected root, fixed keyRef portable-recovery and the existing Secret Service vault callback; browser-supplied paths, arbitrary commands, native route operations, keys and shell are forbidden. The dedicated Gecko-ID host manifest is committed but NOT installed. A native connection owns a single live cipher context, with an owner-only OS flock across simultaneous host processes that is automatically released on process death (without clearing the uncertain effect journal). The host persists CREATE_POSSIBLE before file creation, APPEND_POSSIBLE before each bounded SHA-256-checked fragment, and FINISH_POSSIBLE before finalization. A lost ACK or process death never permits blind replay. Last-known-good and uncertain ciphertext are not automatically deleted. Read-only inspect never initializes a root, repairs, unlocks or creates an archive.

Verification independently opens the tracked ciphertext, authenticates ALL bytes to discard, then reopens the same file and decrypts again while validating frame/reference/donor-byte inventory and SHA-256 equality. This is authenticated inventory only, NOT restorable-fleet proof. A separate restore.begin repeats verification before allowing a second-pass bounded read stream. restore.read produces AUTHENTICATED_SECOND_PASS only after the final tag and unchanged file identity/digest. Interrupted or replaced files never promote partially staged plaintext.

The JavaScript v2 decoder rehydrates exact source base64 and uses the existing donor decoder. The read-only prepareInactiveV2 invokes existing I16 prepareRestoredCanonical to preserve uncertain operations and mark account identities, owner observations, prior approvals, leases and admission inactive. It does not directly activate provider, routing or Git effects. The original I17 batch and slug remain under no-automatic-CREATE/no-automatic-RENAME quarantine.

**Unresolved implementation:** both the original small-case whole-plaintext decoder and a second terminal-gated IndexedDB fragment decoder are present; the latter scans header-bounded frames and reconstructs source/donor/typed canonical state without buffering the whole plaintext archive. It still materializes all unique referenced blobs/canonical rows and the encrypted donor envelope to use PersonaMonkey's existing decoder. These aggregate allocations, real host installation/port authority, full source-heavy fresh-profile guarded donor/canonical apply, 14-file retention and activation proof have NOT been independently reviewed or host-verified. ## Frozen candidate addendum — preliminary F1/F2/F3 correction, October 17

**F1 native writer/lock lifecycle:** Before any native file creation, persist `CREATE_POSSIBLE`; after obtaining the root-level nonblocking OS `flock`, every failing `export.begin` releases that OS lock in the same process, including duplicate run, locked/missing Secret Service vault, exclusive-file open failure, partial header write and failed OPEN_OBSERVED ledger fsync/rename after writer creation. A later distinct run may acquire the released OS lock but **never consumes or replaces the uncertain old run**. A second writer cannot acquire the lock while the original verified writer actually owns it. File/host process crashes release the lock automatically but never erase durable possible-effect history. Separate native tests assert all of these boundaries.

**F2 run-bound independent effect observations:** The browser source cut is made via the existing canonical IndexedDB and PersonaMonkey donor/cookie/GM adapters with a before/after consistency check. On that *same native connection*, `archive.recovery.complete` accepts the exact run ID, verified ciphertext SHA, source/donor preparation SHA and one of two explicit statuses:

## E-06 R1–R6 remediation candidate addendum (October 17; revision under review)

This addendum describes only the code now in PR #24; it does **not** approve the format, relax the native-host installation boundary, or change the fixed AES-256-GCM/PBKDF2 single-message envelope above. Legacy v1 encoding/decoding remains unchanged.

**R1 — export succession and recovery receipts.** Browser `backup:v2:active` and its per-run receipt are updated within **one IndexedDB readwrite transaction**. A successful release is permitted only for an exact matching active run with a complete `AUTHENTICATED_INVENTORY_ONLY` ledger, same ciphertext digest, valid `preparedSha256`, and terminal `RECOVERY_VERIFIED` native qualification. The per-run receipt remains; a stale run cannot delete a newer reservation. A never-dispatched `PREPARED` reservation can be explicitly `RETIRED_PRE_DISPATCH`; no post-`CREATE_POSSIBLE` uncertain effect may be silently declared absent. For lost native qualification ACK, a guarded, read-only `archive.inspect` returns an exact run-bound terminal receipt, and an independent `backup.verify` reopens/authenticates ciphertext before atomic browser reconciliation. No native replay or provider action is allowed. The 14-successful-file pool remains native-only after qualification, with last-known-good exclusion and `DELETE_POSSIBLE` halting pruning.

**R2 — legacy-cap separation.** `snapshotCanonical` continues to enforce the original 64 MiB v1 archive bound. The v2 source cut instead uses `snapshotCanonicalV2` with all five IndexedDB stores in one readonly cursor transaction, followed by a second consistency cut and strict complete-source preflight. V2 compilation deduplicates identical byte-exact source blobs. A synthetic test constructs more than 64 MiB of *pre-deduplicated* repeated historical source without dropping a revision. **Residual explicit resource hold:** its current transaction still materializes rows and dedup/source maps in the extension heap. No worst-case bounded-heap claim is made. The unchanged 4 MiB CANONICAL, 1 MiB END, 2 GiB DONOR and aggregate row/blob limits reject otherwise valid unsupported scale with named errors **before** external dispatch, not truncation. An independently reviewed continuation/transport revision is required if a legitimate record exceeds those constraints.

**R3 — restore inclusion/removal.** An archived `account:<id>` is not re-created where later *reliable destination* `removal:<id>` history has `REMOVED_ONLY_LOCALLY` and a newer revision. Those account rows are excluded in both merge and replace; the newer tombstone and later destination exit history are preserved. Orphan generator records remain historical/unverified with no active account or Persona association. Ambiguous tombstone ordering and conflicting exit histories HOLD. A wholly fresh-profile restore requires an explicit `INCLUDE_INACTIVE` or `EXCLUDE` decision for every archived account; incoming approval is not live authority. **No original-profile write or native route activation is implied.**

**R4 — filesystem identity.** The unregistered Linux native host now pins an owner-only root directory descriptor, uses dirfd-relative no-follow opens for ledger, ciphertext, writer and verification, and atomic journal rename/fsync. The prune operation verifies the exact GCM ciphertext against the durable qualified receipt, persists `DELETE_POSSIBLE`, checks device/inode/size/mtime/ctime before rename, moves the candidate to an unpredictable quarantine entry in the pinned directory, checks the moved device/inode/size/mtime (rename itself changes ctime), then unlinks that quarantine entry and fsyncs. Changed files and lost unlink/fsync ACK remain `DELETE_POSSIBLE` and stop all automatic pruning. Native failure injection tests include symlink, directory replacement, hardlink, open/header failure and retained data. **Threat boundary:** a malicious cooperating same-UID process can still modify inodes concurrently; `flock` only excludes cooperating writers. This requires explicit installation-root ownership/permission and independent host review, not a claim of universal same-UID adversary isolation.

**R5 — exact metadata JSON.** Before source inventory qualification, Python validates UTF-8, lexical UTF-16-ordered unique keys, finite IEEE-754 values and exact source bytes against the canonical JSON token representation also required by the JavaScript decoder. Thus `1.0`, `1e+0`, `-0`, noncanonical exponent zeros, imprecise integers beyond the double precision domain, duplicate keys, NaN/Infinity, invalid UTF-8 and encoded lone surrogate tokens are rejected. Literal `-0` is represented instead by the v2 tagged `NumberNegativeZero` value; an ordinary positive zero uses `0`. The Python/JavaScript adversarial vector suite is part of required D verification. Formal independent review must confirm all numeric/unicode boundary vectors.

**R6 — source discriminator collision.** The v2 compiler rejects a literal `__pcmsType` or `__pcmsV2BlobRef` at any depth in an ordinary source object before any effect, rather than guessing whether it means Date, Undefined, Bytes, negative-zero or a blob reference. Genuine Date, undefined, typed binary views and negative zero continue to roundtrip using the existing typed decoder. The old v1 archive codec is untouched; old pre-encoded v1 synthetic fixture objects cannot be silently treated as raw structured-clone data.

**I16 compatibility repair:** Volatile donor native-status/security/permission *observations* are not portable Persona state. For an **inactive** I16 plan, only durable donor `state` and `containers` determine the destination snapshot digest; a real changed Persona/route/record still invalidates it. Existing controller-activation, protected route-admission, approval and fresh source revalidation gates remain separate and mandatory. No new route capability was added.
