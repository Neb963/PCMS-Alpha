# S02 v2 candidate A — frozen review proposal (NOT APPROVED)

**Authority:** Client v1.0.0 AC-17; Gate B v1.1 GB-03 / E-06. This specifies the byte grammar now emitted by the S02 branch for independent format/security review. It confers no permission to install the native host, modify original profiles or enable v2 backup. Legacy v1 import/export remains unchanged.

## Binary envelope

All numbers are unsigned big-endian. The first 50 bytes are exactly: magic 50 43 4d 53 42 4b 32 00 (PCMSBK2 plus NUL); version 02 (1 byte); algorithm/KDF ID 01 (1 byte); PBKDF2-SHA256 iterations 0003d090 (4 bytes, exactly 250000); OS CSPRNG salt (16 bytes); OS CSPRNG IV (12 bytes); exact plaintext length (8 bytes). The **entire header** is AES-GCM AAD. Follow with exactly that many bytes of ONE AES-256-GCM ciphertext message and a final 16-byte authentication tag, without trailing data. The NIST single-invocation bound is 2^36−32 plaintext bytes. Every new run gets a fresh salt/IV; never reuse an interrupted session's cipher context. No derived key in storage, diagnostics or ciphertext metadata.

## Authenticated plaintext framing

Each frame is 1-byte tag + 8-byte unsigned big-endian length + exactly length bytes. Valid order: BLOB* → CANONICAL* → DONOR → END. Unknown tags, unexpected ordering, trailing bytes and duplicate entries are invalid. Transport fragments may split these frames at arbitrary offsets. They are NOT separately encrypted or authenticated messages.

- **BLOB / tag 01:** 32 raw bytes of SHA-256 digest followed by original raw file bytes. ID equals SHA-256(raw bytes), including binary assets. At most one occurrence per digest; path is retained in the original source manifest rather than invented from a digest. Candidate frame limit 12 MiB + 32 bytes (matching current source-file bound).
- **CANONICAL / tag 02:** canonical sorted-key UTF-8 JSON with exactly store, key, value and refs. Store is one of entities, operations, events, meta, observations. Key and value retain the exact existing PCMS structured-clone taxonomy (including Undefined, Date, ArrayBuffer, typed arrays). Source-bearing records retain complete original/current/previous-good/candidate/history manifests and identifiers, but their original source blob base64 field is replaced by an exact one-key object with property __pcmsV2BlobRef and the lowercase content SHA-256 value. The refs array contains sorted unique source digests referenced by that row. Never infer bytes from merely a fingerprint. Candidate max 4 MiB per deduplicated metadata row; a legitimate larger record requires independently reviewed continuation, not truncation.
- **DONOR / tag 03:** exactly the original encrypted PersonaMonkey portable backup envelope as raw UTF-8 bytes. The native parser authenticates outer GCM and donor byte SHA; the unchanged donor decoder must independently decrypt and validate this inner envelope before restore. Maximum prototype frame 2 GiB; actual donor headroom is not yet measured.
- **END / tag ff:** UTF-8 sorted-key JSON with EXACTLY schema:2, canonicalRows, storeCounts (all five stores), uniqueBlobs, donorSections:1, sourceRefsSha256, rowDigestsSha256, donorSha256. sourceRefsSha256 hashes sorted lowercase referenced digests joined by LF; the referenced set must exactly equal actual BLOB IDs. rowDigestsSha256 hashes lowercase SHA-256 digests of CANONICAL raw frame payloads, in order, joined by LF. donorSha256 hashes exact DONOR bytes. At most 1 MiB END payload.

JSON key ordering follows JavaScript UTF-16 lexical key ordering. The native parser rejects duplicate and out-of-order object keys, invalid UTF-8, nonfinite number tokens, malformed/oversized frames, duplicate row identities, mismatched content digests and terminal inventory. Parser limits are checked from the header BEFORE metadata allocations: up to 100,000 CANONICAL rows and 100,000 unique blobs per candidate. These explicit resource bounds remain subject to real fleet sizing and independent review; none permit omitting evidence. Large numeric JSON canonicalization/interoperability and oversized legitimate single-record continuation remain review findings, not silently accepted constraints.

## Effect, verification and restoration boundary

The fixed-purpose native candidate uses host-selected root, fixed keyRef portable-recovery and the existing Secret Service vault callback; browser-supplied paths, arbitrary commands, native route operations, keys and shell are forbidden. The dedicated Gecko-ID host manifest is committed but NOT installed. A native connection owns a single live cipher context, with an owner-only OS flock across simultaneous host processes that is automatically released on process death (without clearing the uncertain effect journal). The host persists CREATE_POSSIBLE before file creation, APPEND_POSSIBLE before each bounded SHA-256-checked fragment, and FINISH_POSSIBLE before finalization. A lost ACK or process death never permits blind replay. Last-known-good and uncertain ciphertext are not automatically deleted. Read-only inspect never initializes a root, repairs, unlocks or creates an archive.

Verification independently opens the tracked ciphertext, authenticates ALL bytes to discard, then reopens the same file and decrypts again while validating frame/reference/donor-byte inventory and SHA-256 equality. This is authenticated inventory only, NOT restorable-fleet proof. A separate restore.begin repeats verification before allowing a second-pass bounded read stream. restore.read produces AUTHENTICATED_SECOND_PASS only after the final tag and unchanged file identity/digest. Interrupted or replaced files never promote partially staged plaintext.

The JavaScript v2 decoder rehydrates exact source base64 and uses the existing donor decoder. The read-only prepareInactiveV2 invokes existing I16 prepareRestoredCanonical to preserve uncertain operations and mark account identities, owner observations, prior approvals, leases and admission inactive. It does not directly activate provider, routing or Git effects. The original I17 batch and slug remain under no-automatic-CREATE/no-automatic-RENAME quarantine.

**Unresolved implementation:** both the original small-case whole-plaintext decoder and a second terminal-gated IndexedDB fragment decoder are present; the latter scans header-bounded frames and reconstructs source/donor/typed canonical state without buffering the whole plaintext archive. It still materializes all unique referenced blobs/canonical rows and the encrypted donor envelope to use PersonaMonkey's existing decoder. These aggregate allocations, real host installation/port authority, full source-heavy fresh-profile guarded donor/canonical apply, 14-file retention and activation proof have NOT been independently reviewed or host-verified. No v2 production activation or E-06 acceptance is claimed.

## Frozen candidate addendum — preliminary F1/F2/F3 correction, October 17

This addendum is a **review-candidate clarification**, not an independent E-06 approval. The external binary envelope's 50-byte header, 16-byte tag and the four plaintext frame type numbers remain as specified above. The existing fixed deterministic test vector is unchanged; it is never used as real entropy.

**F1 native writer/lock lifecycle:** Before any native file creation, persist `CREATE_POSSIBLE`; after obtaining the root-level nonblocking OS `flock`, every failing `export.begin` releases that OS lock in the same process, including duplicate run, locked/missing Secret Service vault, exclusive-file open failure, partial header write and failed OPEN_OBSERVED ledger fsync/rename after writer creation. A writer that opened but whose success is uncertain is abandoned (FD closed, AES-GCM context spent), not finalized or retried. Preserve its `CREATE_POSSIBLE` ledger and any possible ciphertext. A later distinct run may acquire the released OS lock but **never consumes or replaces the uncertain old run**. A second writer cannot acquire the lock while the original verified writer actually owns it. File/host process crashes release the lock automatically but never erase durable possible-effect history. Separate native tests assert all of these boundaries.

**F2 run-bound independent effect observations:** The browser source cut is made via the existing canonical IndexedDB and PersonaMonkey donor/cookie/GM adapters with a before/after consistency check. The existing I15 daily claim or reviewed-only manual method records intent before native dispatch. Every native `ok:true` per-run reply carries its exact `s02_<32hex>` run ID. The browser port rejects an unbound/mismatched run reply; an observed source count or tag never authorizes importing Personas. Native `restore.begin` requires a tracked `WRITTEN_UNVERIFIED` or already `RECOVERY_VERIFIED` archive and performs independent two-pass AEAD/file verification before returning bounded chunks. `restore.read` sequences cannot be replayed or continued after a crash/lost ACK. The final read returns `AUTHENTICATED_SECOND_PASS` only after entire-file GCM tag verification and file identity and SHA-256 comparison. On that *same native connection*, `archive.recovery.complete` accepts the exact run ID, verified ciphertext SHA, source/donor preparation SHA and one of two explicit statuses:
- `READONLY_RECOVERY_VERIFIED`: full canonical/source asset/history and encrypted donor envelope have been independently decoded from the file into an **inactive read-only backup self-test**; no source/donor import was performed.
- `INACTIVE_PREPARED_NOT_APPLIED`: existing I16 sanitizer constructed a fail-closed inactive recovery candidate with mapped identities and held approvals, but full fresh-profile donor/canonical application remains separately gated.

The host then independently reopens/authenticates the same ciphertext again and persists `RECOVERY_VERIFIED` with the prepared digest and nonzero verification timestamp. **Only recovery-qualified files** count towards the native successful-file retention pool. A native `AUTHENTICATED_SOURCE_INVENTORY` or browser read without independent source/donor verification is never a success. The same I15 daily store supports `AUTO_NATIVE` tier 3 historical receipts with native run SHA, prepared digest and exact run day. V1 `AUTO` tier 2 Downloads receipts retain their unchanged structure and retention code; no successful tier can be promoted by a UI-provided fake ACK. All pre-E-06 tests that inject synthetic native effects are labeled as such.

**14-successful-file retention and lost-ACK:** The native fixed-root candidate scans only same-root, root-owned, regular, single-link recovered ciphertext ledgers; 14 most recent `RECOVERY_VERIFIED` files and the last known-good are protected. A fixed policy prohibits deleting a held/uncertain/nonexistent/moved/colliding file. Before any eligible older-file removal, verify its actual SHA/GCM on disk, persist `DELETE_POSSIBLE`, unlink under the exclusive root writer lock and fsync the directory, then persist `REMOVED`. Missing unlink ACK or ambiguous restart leaves `DELETE_POSSIBLE` and prevents *any* further automatic prune. Exact file paths never originate from browser messages. **Openat/dirfd-based root/file atomicity is not yet formally proved**; symlink/rename races remain for independent E-06 review and must be resolved before production host registration.

**F3 source/donor fleet:** The diverse D candidate exercises 50 historical accounts, 1,024 source-bearing revisions (original/current/previous manifests), 3,332 unique raw binary/text source blobs, 1,074 canonical records, and 50 PersonaMonkey portable donor Personas/scripts/cookie sets/GM sets. The installed Firefox fixture additionally measures temporary IndexedDB usage over 1,024 distinct source revisions. No source/count truncation or generator/file selection may occur merely to satisfy a limit. Memory reports are *measured point samples* from disposable runners and do not guarantee fleet maxima.

**Transient staging confidentiality:** A dedicated inactive Firefox IndexedDB store holds **only AES-256-GCM sealed chunks and fresh IVs**, not plaintext or a decryption secret. Its per-run nonextractable key exists only in the extension's volatile module memory; an event-page cold restart makes an interrupted stage **unreadable and HELD**, never restart-resumable or authority-conferring. After qualified recovery, the guarded coordinator drops the staged ciphertext and volatile key. This is temporary staging only, not a second portable backup. Exported ciphertext is persisted only in the fixed native root, not through plaintext temporary archive files.

**Structured-clone and numeric lexical grammar:** Existing strict `serializeClone` retains Undefined, Date, ArrayBuffer, typed arrays and finite numbers; unsupported classes or nonfinite numbers fail closed. The v2-only explicit `{"__pcmsType":"NumberNegativeZero"}` tag preserves JavaScript IEEE-754 negative zero, which ordinary JSON would silently convert to positive zero; legacy v1 encoder is unchanged, and its decoder accepts the new tag only on reviewed v2 restores. Object keys are sorted by JS UTF-16 code units and are unique; Python rejects invalid UTF-8, duplicate/out-of-order keys and NaN/Infinity. JSON finite-number lexical agreement (exponents/trailing zeros, large integers, signed zero, lone Unicode surrogate differences) must be independently reviewed across Python and Firefox: the JS restore decoder rejects any metadata whose encoded bytes differ from its strict `canonicalJSON` rendering. A valid deduplicated row over the current **4 MiB CANONICAL** or **1 MiB END** prototype limits is explicitly rejected before allocating/dispatching, **never truncated**. A genuine case exceeding reviewed bounds requires a compatible independently reviewed continuation/frame version, not invented omission or arbitrary dataset down-selection.
